# Step 0.5: クエリログの整形表示 & ブレークポイントデバッグ（Zed）

← [Step 0](./00-docker-uv-mysql.md) ／ [目次](./README.md) ／ 次: [Step 1](./01-application-factory.md)

## 🎯 目的

アプリ本体を書き始める**前に**、開発中ずっと使う「見る道具」を2つ仕込む。

1. **クエリログの整形表示** … アプリが発行した SQL を、実行時間つき・複数行に整形してターミナルに出す
2. **ブレークポイントデバッグ（Zed）** … 任意の行で処理を止め、変数やコールスタックを覗く

> **これは核（開発環境）。** 「何が起きているか」が最初から見えると、Step1 以降の理解速度が段違いになります。バグ調査も推測でなく観測でできます。
> **補足: ターミナル版デバッグ（`breakpoint()`）や DB 側の全ログ（MySQL general_log）**。

### なぜ「アプリを作る前」に入れるのか

このステップでやるのは **環境の仕込み**です:
- 依存（`sqlparse` / `debugpy`）を追加
- `flaskr/sql_debug.py`（ログ整形モジュール）を置く
- `.zed/debug.json`（Zed のデバッグ設定）を置く

これらは**アプリ本体が無くても用意できます**。そして [Step 1](./01-application-factory.md) でファクトリに2行足すと自動で有効化され、[Step 2](./02-database-sqlalchemy.md) で最初のクエリが流れた瞬間から整形ログが見えます。「後付け」ではなく最初から観測できる状態にしておくのが狙いです。

> ⚠️ 前提: [Step 0](./00-docker-uv-mysql.md) の `uv init` は済んでいること（`flaskr-api/` に `pyproject.toml` がある）。`flaskr/` フォルダも作成済み（中身は空でOK）。


> 💡補足: どちらも `--dev`（開発依存）です。本番イメージ（[Step 6](./06-frontend-and-wrapup.md) の `uv sync --no-dev`）には含まれません。

## 0.5-2. クエリログを整形表示する

### コード

`flaskr/sql_debug.py` を新規作成（`flaskr/` の中。`__init__.py` はまだ無くてOK）:

```python
import time
from typing import Any

import sqlparse
from sqlalchemy import event
from sqlalchemy.engine import Engine


def enable() -> None:
    """実行された SQL を「整形＋実行時間」でターミナルに表示する（開発時のみ有効化）。"""

    @event.listens_for(Engine, "before_cursor_execute")
    def _before(
        conn: Any, cursor: Any, statement: str,
        parameters: Any, context: Any, executemany: bool,
    ) -> None:
        # クエリ開始時刻を積む（ネスト対応でリストに push）
        conn.info.setdefault("_qstart", []).append(time.perf_counter())

    @event.listens_for(Engine, "after_cursor_execute")
    def _after(
        conn: Any, cursor: Any, statement: str,
        parameters: Any, context: Any, executemany: bool,
    ) -> None:
        elapsed_ms = (time.perf_counter() - conn.info["_qstart"].pop()) * 1000
        # SQL を複数行に整形（キーワードは大文字に）
        pretty = sqlparse.format(statement, reindent=True, keyword_case="upper")
        # ANSI カラー: シアンの見出し / 黄色のパラメータ
        print(f"\n\033[36m── SQL  ({elapsed_ms:.1f} ms) ──\033[0m")
        print(pretty)
        print(f"\033[33mparams:\033[0m {parameters}\n")
```

### 有効化は Step 1 のファクトリで（先に説明だけ）

このモジュールは、[Step 1](./01-application-factory.md) の `create_app()` に次の2行を入れると有効になります（**Step 1 のコードには反映済み**なので、そのまま写経すればOK）:

```python
    # デバッグ起動時（--debug）だけ、SQL 整形ログを有効化する
    if app.debug:
        from . import sql_debug
        sql_debug.enable()
```

### 🧠 解説

- `event.listens_for(Engine, ...)` … SQLAlchemy が **どのクエリを実行する時も**呼ばれるフックを仕掛けます。`before` で開始時刻を記録し、`after` で経過時間を計算して表示。
- `app.debug` ガードが要点。`uv run flask ... run --debug` の時だけログが出て、テストや本番では静かなままです。
- 🔗 **接続**: Step3 で出てくる `@bp.before_app_request`（リクエスト前フック）と同じ「イベントに関数を差し込む」発想です。対象が「リクエスト」か「SQL実行」かの違いだけ。

> 💡補足（もっと手軽な代替）: 整形不要なら Step1 のファクトリ設定に `SQLALCHEMY_ECHO=app.debug` を足すだけでも生SQLは出ます。ただし1行べた書きで見づらいので、本教材は上の整形版を採用します。

### 🔮 予測 → 動作確認（アプリ無しで今すぐ試せる）

**実行前に予想してみよう:** `sqlparse` は1行のSQLをどう整形する？ キーワードは大文字になる？

```bash
uv run python -c "import sqlparse; print(sqlparse.format('select id,title from post where id=1 order by created desc', reindent=True, keyword_case='upper'))"
```
期待される出力（複数行に整形され、キーワードが大文字）:
```sql
SELECT id,
       title
FROM post
WHERE id=1
ORDER BY created DESC
```
これが出れば整形の仕組みは完成です。**実際のアプリのログは、[Step 2](./02-database-sqlalchemy.md) で `flask ... run --debug` 中に API を叩いた時**に、この形＋実行時間つきで流れます。

> 💡補足（DB側で全部拾う別解）: `docker-compose.yml` の `command:` に `--general-log=1 --general-log-file=/var/lib/mysql/general.log` を足すと MySQL 自身の全クエリログも取れます。ただし接続/切断まで含み**未整形で冗長**なので、「見やすく整形」目的なら上のアプリ側が最適です。

## 0.5-3. Zed でブレークポイントデバッグ

この教材構成では **Flask はPC上のプロセス**（Dockerの中ではない）なので、リモートデバッグ不要でそのまま止められます。

### コード（デバッグ設定）

`flaskr-api/.zed/debug.json` を新規作成。**attach（推奨）と launch の2つ**を入れておきます:

```json
[
  {
    "label": "Flask (attach :5678)",
    "adapter": "Debugpy",
    "request": "attach",
    "connect": { "host": "127.0.0.1", "port": 5678 }
  },
  {
    "label": "Flask (debug)",
    "adapter": "Debugpy",
    "request": "launch",
    "module": "flask",
    "cwd": "$ZED_WORKTREE_ROOT",
    "env": { "FLASK_APP": "flaskr", "FLASK_DEBUG": "1" },
    "args": ["run", "--no-reload", "--no-debugger"]
  }
]
```

> 📌 **なぜ2つ？** Zed のデバッガは「開いているフォルダの Python 環境（toolchain）」で interpreter を決めます。**親リポジトリ（`roadmap-sh-flask`）を開いていると venv を見つけられず**、`launch` は `No module named flask` で失敗します。**attach 方式なら自分で `uv run`（正しい venv）でサーバーを起動して Zed が繋ぐだけ**なので、どのフォルダを開いていても確実に動きます。

### 方法A（推奨）: アタッチ方式 — 親リポジトリを開いたままでOK

docs とコードを同時に見られて、venv 検出の事故も無い、一番安定した方法です。

1. 止めたい行の**ガター（行番号の左）をクリック**して赤い●を置く
2. ターミナル（`flaskr-api/`）で**デバッグ待受サーバー**を起動:
   ```bash
   uv run python -m debugpy --listen 127.0.0.1:5678 --wait-for-client \
     -m flask --app flaskr run --debug --no-reload --no-debugger
   ```
   → `--wait-for-client` で「Zed が繋ぐまで待機」状態になる
3. Zed の Run/Debug パネル → **"Flask (attach :5678)"** を起動 → 接続された瞬間にサーバーが動き出す
4. ブラウザ/curl でエンドポイントを叩く → **● で停止**。変数パネル・コールスタックで調査
5. ステップ実行: **Step Over / Step Into / Continue**

### 方法B: launch 方式 — flaskr-api をプロジェクトとして開く場合

親を開かず `flaskr-api/` 単体で作業するなら、こちらがボタン1つで手軽です。

1. **Zed で `flaskr-api/` をプロジェクトとして開く**（親フォルダだと venv を見つけられず失敗）
2. 下部ステータスバーが **`Python 3.x (flaskr-api; uv)`** を示すのを確認（違えばクリックして `.venv` を選ぶ）
3. ●を置く
4. Run/Debug パネル → **"Flask (debug)"** を起動（⚠️ ターミナルからではない）
5. curl で叩く → **● で停止**

### 🧠 解説（なぜこの設定か）

- `"adapter": "Debugpy"` … Zed が Python を止めるのに使うアダプタ（`debugpy`。0.5-1 で追加済み）
- **attach**: `request: "attach"` + `connect(host/port)` … 既に動いている debugpy 待受プロセスに Zed が接続する。interpreter は `uv run` 側が決めるので Zed の環境検出に依存しない（＝堅牢）
- **launch**: `module: "flask"` + `args: ["run", ...]` … `flask run` を Zed のデバッガが**直接起動**する。interpreter は「開いているフォルダの toolchain」で決まる
- `FLASK_DEBUG=1` / `--debug` … `app.debug` が True になり、**0.5-2 のSQL整形ログも同時に有効**になる
- ⚠️ `--no-reload --no-debugger` が最重要:
  - `--no-reload`: Flask の自動リロードは別プロセスを起動するため、デバッガが見失う。切る。
  - `--no-debugger`: Werkzeug の「例外時ブラウザデバッガ」を切る（例外は Zed 側で止めたいため）

**セッションを止める・閉じる:** デバッグパネル上部ツールバーの **⏻（電源マーク）= Stop/Terminate** で終了。右端の **×** でパネルを閉じる（コマンドパレット `debugger: stop` でも可）。上部のセッション名が**取り消し線**なら、既に終了済み（＝止める必要なし）。

> ⚠️ **最重要の勘違いポイント**: ガターの●は「**Zed のデバッガに繋がっているプロセス**」にだけ効きます。繋がるのは次のどちらか:
> - **方法A（attach）**: `uv run python -m debugpy ...` で起動 → Zed が "Flask (attach)" で接続
> - **方法B（launch）**: Zed の Run/Debug パネルから "Flask (debug)" で起動
>
> 一方、**ただ `uv run flask ... run` しただけのサーバー**（Zed内蔵ターミナルでも別ターミナルでも）は**デバッガと繋がっていない**ので、●は効きません。その場合は ●ではなく **`breakpoint()`（下記）** を使ってください。

> 実際に止められるのは、当然ながら**コードを書いた後**（[Step 1](./01-application-factory.md) 以降）です。今はまだ設定だけ置いておきます。

### 補足: ターミナルだけで止める（IDE不要・最速）

Zed を起動しなくても、止めたい行に Python 標準の `breakpoint()` を書けば pdb が起動します:
```python
def index():
    breakpoint()          # ← ここで pdb が起動
    ...
```
起動（**リローダを切る**のがコツ）:
```bash
uv run flask --app flaskr run --debug --no-reload
```
pdb 内では `n`(次) / `s`(中へ) / `c`(継続) / `p 変数名`(値表示) / `q`(終了)。

### 🔮 予測 → 動作確認（アプリ無しで今すぐ試せる）

**実行前に予想してみよう:** 次を実行すると、`print(x)` の前で止まる？ 止まったら `p x` で何が出る？

```bash
uv run python -c "x = 42; breakpoint(); print(x)"
```
期待される挙動: `(Pdb)` プロンプトが出て**停止**。`p x` と打つと `42`、`c` で継続して `42` が出力される。
→ これで「止める・覗く」の仕組みが今すぐ確認できます。Zed の GUI 停止も同じことを画面でやるだけです。

## 0.5-4. つまずきポイント

| 症状 | 原因 | 対処 |
|---|---|---|
| `ModuleNotFoundError: sqlparse` | 依存未追加 | `uv add --dev sqlparse` |
| SQLログが出ない | `--debug` を付けていない / `app.debug` が False | `run --debug` で起動。Zed 設定は `FLASK_DEBUG=1` を確認 |
| ログの色が化ける（`\033[36m` が見える） | 端末が ANSI 非対応 | iTerm2/Zed のターミナルなら対応。気になれば色コードを消してよい |
| Zed のブレークポイントで止まらない | リローダが有効 | `args` に `--no-reload` があるか確認。`FLASK_DEBUG=1` だけだとリローダが動く |
| **`No module named flask`**（`~/.local/bin/python3` で起動） | launch方式で、Zed が `.venv` でなくグローバル python を使っている（親リポジトリを開いていると起きやすい） | **方法A（attach）に切り替えるのが確実**（`uv run` が venv を使うので事故らない）。launch にこだわるなら `flaskr-api/` を単体で開く＋ステータスバーで `.venv` を選択 |
| Zed が debugpy を見つけない | アダプタ未導入 / venv 未選択 | `uv add --dev debugpy`。Zed が `flaskr-api/.venv` を使っているか確認 |
| pdb 起動後すぐ抜ける/乱れる | リローダの子プロセスと競合 | `run --debug --no-reload` で起動する |

## ✅ 想起チェック

**見ないで説明してみよう:** SQL整形ログとブレークポイントを、なぜ `app.debug` / `--debug` の時だけ有効にするのか？

<details><summary>解答例</summary>

本番やテストで有効だと、**大量のログでうるさく、わずかに遅く**なり、`breakpoint()` が残っていると**本番で処理が止まる**事故にもなるため。開発時（`--debug` / `FLASK_DEBUG=1`）だけ ON にすることで、観測性は開発中に得つつ、本番は静かで速いままにできる。
</details>

**小問:** Zed のデバッグ設定で `--no-reload` を付けるのはなぜ？

<details><summary>解答例</summary>

Flask の自動リロード機能は、コード変更を監視するために**アプリを別の子プロセスで起動**する。デバッガは最初のプロセスに接続しているため、子プロセスで動く実際のコードを見失い、ブレークポイントで止まらなくなる。`--no-reload` でリロードを切ると、デバッガが接続したプロセスがそのままアプリを実行するので確実に止まる。
</details>

## まとめ

- **クエリログ整形**: `sqlparse` + SQLAlchemy の `after_cursor_execute` フックで、実行SQLを「整形＋実行時間」表示。`app.debug` 時のみ
- **Zed デバッグ**: `.zed/debug.json`（Debugpy）＋ ガターで●。`--no-reload --no-debugger` が肝
- **ターミナル版**: `breakpoint()` + `run --debug --no-reload`
- どちらも**今は設定だけ**。Step 1 のファクトリで有効化され、Step 2 の最初のクエリから効き始める

準備ができたら [Step 1: アプリケーションファクトリ](./01-application-factory.md) へ。ファクトリに SQL ログ有効化の2行が入っています。
